## Bytebefund

Frische native Ausgangsmessung auf dem freigegebenen Planstand: Routes
**100/100 PASS**, authentifiziert 8059 B, Passwortschutz aus 8058 B.
Die C++-Compilerprobe zaehlt die tatsaechlichen UTF-8-Konstanten mit `sizeof-1`:
Ausgangssuffix 6662 B, Kandidat **9013 B**. Der unveraenderte authentifizierte
Kopf ist 8059-6662 = **1397 B**. Daraus folgt ohne Schaetzung:

| Zustand / Grenze | Bytes |
|---|---:|
| Kandidat angemeldet, einstellige Sequenz | **10410** |
| Kandidat Passwortschutz aus, einstellige Sequenz | **10409** |
| Kandidat angemeldet, 20-stellige Sequenz (+19 B) | **10429** |
| Unveraenderte harte Grenze | **8192** |
| Zulaessiger Normalbody bei bestehender 128-B-Reserve | **8064** |
| Fehlbetrag zur harten Grenze, angemeldet | **2218** |
| Fehlbetrag einschliesslich Normalreserve | **2346** |

Dies ist die komplette Kandidatenlaenge aus nativer Kopf-Baseline plus
compilerverifizierter Konstante, **kein ausgelieferter 10410-B-HTTP-Body**.
Der unveraenderte produktive Groessenguard wuerde stattdessen vollstaendig
503 `web-shell-unavailable` ohne Suffix liefern; der bestehende native
Overflow-/Suffix-Fehlervertrag bestand in der Ausgangssuite. Ein Aufweichen
dieses Guards zur Messung oder Auslieferung fand nicht statt.

Rein arithmetisch benoetigte genau dieser Normalbody mit 128 B Reserve
10538 B; dies ist **kein vorgeschlagener oder qualifizierter Grenzwert**.
Auch die nicht freigegebene Planalternative 10240 B allein wuerde diesen
Kandidaten mit Reserve noch um 298 B verfehlen. Der Befund beweist keinen
universellen Unmoeglichkeitssatz fuer jede denkbare 8192-B-Implementierung.
