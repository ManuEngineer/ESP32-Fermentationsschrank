## 2. Messung (ein Boot, ein authentifizierter Client)
Ablauf: Reset, 75 s Idle, Login + Shell, 120 s Polling (3 parallele GETs im 5-s-Takt), Intents abgelehnt/„unavailable“,
Gerätename setzen/zurücksetzen (Client `heap_run.py`, [Skript](PR209_Q4_HRAM2_HEAP_RUN.py.txt)), danach Browser-/Funktionstest im selben Boot.
HWM-Werte sind kumulativ seit Taskstart; Task-Stack 8 704 B.

| Phase (UART-Zeit) | frei intern min. [B] | `minimum_free_heap`/`internal_min` [B] | größter Block min. [B] | HTTPD-Stack-HWM min. [B] |
|---|---|---|---|---|
| Idle 0–75 s (30-s-Probe) | 41 960 | 33 060 | 32 768 | – |
| Login + Shell | 33 928 | 29 120 | 30 720 | 2 764 |
| Polling (120 s) | 30 284 | 26 888 | 26 624 | 2 636 |
| Mutationen + Namenscommit ×2 | 36 068 | 26 136 | 28 672 | **2 236** |
| Browser-/Funktionstest (≈ 30 min, mehrere Sessions, Assets) | 24 752 | **17 104** | **18 432** | 2 236 |
| Gesamt | 24 752 | 17 104 | 18 432 | **2 236** |

**Stack:** größte Nutzung 8 704 − 2 236 = **6 468 B** – identisch zur 8 192-B-Basis (8 192 − 1 724 = 6 468 B) bei
vergleichbarer Pfadmenge; Rest damit exakt **+512 B**. Auch die Browserphase (Login, Namenscommit, Asset-Last) hat die
Nutzung nicht erhöht.

**Vergleich zur 8 192-B-Basis (Idle, erste 30-s-Probe; je eine Messung):** `free_heap` 42 692 → 42 128 B (−564 B, erwartet −512 B);
`minimum_free_heap` 34 400 → 33 060 B (−1 340 B; Boot-Tiefststand schwankt mit WLAN-Initialisierung, **nicht** dem Stack allein
zuzuordnen); größter Block unverändert 32 768 B; Main-Stack-HWM 11 272 → 11 144 B. Das Polling-Fenster ist hier 120 s statt
600 s und nicht strikt vergleichbar (8 192: frei 25 460 / `internal_min` 22 428 / Block 22 528 B); daraus wird **kein**
statistischer Heapvergleich abgeleitet.

**Browserphase:** Tiefststand 17 104 B (`internal_min`) und größter Block 18 432 B traten bei Asset-Anfragen mit mehreren
gleichzeitigen Browserverbindungen auf (~290 s bzw. ~209 s UART-Zeit); danach erholte sich der Heap (letzte 30-s-Probe: frei 41 836 B,
größter Block 31 744 B). Das ist **ohne** Vergleichsbasis für 8 192 B und ein neuer, schlechterer Tiefststand als im
Polling. Er ist als Risikoindikation für `ESP32_LARGEST_FREE_BLOCK` zu werten, nicht als Fehler (kein Alloc-Fehler).

## 4. Funktionstest Gerätename und Fehlermeldungen
Einstellungen → Name → „Speichern“ → Bestätigung „Sicher?“ (zweistufig).
| Fall | HTTP/Ergebnis | UI |
|---|---|---|
| Leerer Name | 400, Name bleibt unverändert | **keine** sichtbare Fehlermeldung (Feld springt auf den bisherigen Namen) |
| Name 60 Zeichen (> 48) | 422 `rejected`, Name unverändert | „Abgelehnt“ sichtbar |
| `<Name>-t` | 200 `applied` | „Erledigt“; nach Reload bleibt der neue Name |
| Zurücksetzen auf Original | 200 `applied` | „Erledigt“; nach Reload Originalname (Gerät = Ausgangsname) |
| Falsches Passwort | API `401 invalid-credentials` | **keine** Meldung; Seite bleibt auf Login (`app.js`: `if(r.ok)location.reload();`) |

**Befunde (nicht korrigiert, Owner/Folgeauftrag):** (B-1) Falsches Passwort zeigt keinen Fehlertext. (B-2) Leerer Name
(HTTP 400) zeigt keine Meldung. (B-3) Sessions werden bei Abbruch ohne Logout nicht freigegeben: nach mehreren nicht
abgemeldeten Browser-/Skriptsitzungen lieferte `login` `503 session-unavailable`, bis die Sessions nach 30 min Idle
(`kWebSessionIdleLimitMs`) abliefen; die Testsitzungen wurden später korrekt abgemeldet. Dies war ein Testhygiene-Fehler
(Sitzungen nicht beendet), die Begrenzung selbst ist erwartetes Verhalten.
